### 2026-09-20 — Snippet Library storage guard (PR #29, merged)

- Root cause of the Snippet Library button silently doing nothing on click: `snippet-library-store.js`'s `storageGet`/`storageSet` called `chrome.storage.local` directly with no guard. Once a page's content script outlives the extension (a reload while the tab stays open, or the service worker's normal idle-teardown/wake cycle catching it at the wrong moment), that call throws synchronously and the rejection went unhandled — `Uncaught (in promise) Error: Extension context invalidated`.
- `mini-ide.js` already solved this for its own storage read back on 2026-09-10 (see the Reliability entry above) but the fix was never applied to this sibling file. Same pattern now applied: `chrome.runtime?.id` liveness check plus try/catch fallback added to `hasChromeStorage()`/`storageGet`/`storageSet`.
- Also removed a premature `console.warn` in `css-snippets.js`'s `switchToComponentAndGetTextarea` that fired before its own 5-attempt retry loop even ran, polluting the error log on ordinary render delay rather than real failure. The loop's existing final-failure warning already covers the real case.
- Open follow-up, not yet actioned: this same "guard against Extension context invalidated" logic now exists independently in two files. Worth a shared utility so the next file that touches `chrome.storage` directly doesn't miss it a third time. Also worth revisiting whether this same class of bug explains other "toolkit went quiet mid-session" reports beyond this one confirmed instance.

### 2026-10-14 — Vanity approval, selector tools, skin copy rework (branch `updates/2026-10-12`)

- **Vanity domain approval:** the toolbar popup now opens by itself on an unapproved https site whose URL starts with `/admin` or `/designcenter` (`vanity-approval-popup.js`). It is reliable across alt-tab: an unanswered popup reopens when the tab or window regains focus (max 3 times per host per session, 15s apart), and "handled" means the user pressed Trust or "Don't ask again", not that it opened. The per-tab URL is kept for the life of the tab (Chrome hides it from an auto-opened popup that has no `activeTab` grant); the pending-trust window is 5 minutes. A green-dot icon cue (`declarativeContent`, Chrome-side matching, new permission) marks CivicPlus-looking pages. No script runs on the site until the user approves Chrome's own exact-origin prompt.
- **Toolkit loading on refresh (long-standing, intermittent):** detection resolved on the first lane found, and on a known host one Live Edit marker is enough, so some refreshes loaded only the Live Edit tool set and every Admin-only tool was missing. On admin/Design Center URLs the bootstrap and the popup now wait for the Admin lane; the detector deadline still falls back. The delivery state now records the lanes sent (`__cpToolkitActivationDeliveryState[...].lanes`).
- **Fancy Button Builder:** "Update selectors" button (green/red/neutral outline) adds the missing `.fancyButton1` or real-ID selector across all style boxes, additive only, nothing saved until the button is saved. New toolbar "Copy selector" button for Fancy Button and widget-skin Advanced Styles boxes, and (generic label-as-selector path) content/structural container boxes, navigation menu boxes (flyouts, left-nav accordion) and site-wide default style boxes (see `graphic-link-fancy-button-selector-copy.md`). The button opens a menu: Copy selector, three built-in `@media (min-width: ...)` blocks (40em, 63em, 2200px) that wrap the same selector and are already closed, and up to 8 user-added media queries stored in `chrome.storage.local`. A Prefix row (None, `.row.outer.wide`, `.row.outer:not(.wide)`, up to 8 user-added) puts a parent selector in front of everything copied, including the media queries; the choice is remembered. Widget skin boxes also get a "Widget row" choice (`.row.wide`, `.row:not(.wide)`) inserted after `.widget.skinN`. The menu is a fixed 320px and fits small laptop screens (scrolls the media list instead of growing). The container/menu/site-style label layout was not seen live when written; the button flashes red if it cannot read a label.
- **Popup / editor:** CSS Snippets has its own toggle and sidebar button (Mini IDE row is a plain toggle). Pseudo override toolbar button removed, along with the Theme Manager re-init check that depended on it (leaving that check without the button would have re-initialised every textarea repeatedly); the options-page setting and `theme-manager-enhancer` are unchanged.
- **Small fixes:** Manage Fonts filter re-adds itself after the modal is reopened (the modal element is reused with rebuilt contents); Insert Powered By no longer adds a `<style>` block (the Powered By skin carries those rules); black LinkedIn and Mastodon social icons replaced.
- **Skin copy rework — flagged, may need to be reverted after rollout.** It changes when copies are saved and cannot be tested against every widget type or amount of advanced-style CSS. Copy Skin no longer saves per copy; each copy is remembered with the unsaved skin it created; the next Save assigns real IDs and `fix-copied-skin-references-helper.js` repairs every copy in one pass, with one summary. New-skin previews are dismissed only in `data-cprole="contentContainer"` (the main container is left alone), Manage Widget Skins is reopened, and a shared overlay (`skin-operation-overlay-helper.js`, Dismiss button plus failsafe timer) covers the CMS re-render. Open: after a copy the main container's preview was still seen disappearing; the toolkit never clicks it, so a console warning now records when it vanishes, to find out what removes it. To revert, drop the commits touching `widget-skin-default-override-helper.js`, `fix-copied-skin-references-helper.js`, `skin-operation-overlay-helper.js` and their two loaders.
- Not run: `node tests/*.test.js` (no Node on the authoring machine). Everything above was reviewed by reading and live-checked by the owner, not machine-tested.

### 2026-10-19 — 1.2.1 late patch

- **Fix:** the View All visited-state custom styles on the 11 gray View All skin defaults (7 Calendar, 4 News Flash) set `background-color: #CC0020` while the normal state is `#757575`, so a visited View All button turned red. Visited background is now `#757575`. This was found after the 1.2.0 submission, hence the patch.
- **Release prep:** version `1.2.1` in `manifest.json` and `js/background/service-worker.js`; new 1.2.1 entry in `html/changelog.html` (the extension opens the changelog on update and highlights entries newer than the user's previous version, so the entry's `v1.2.1` class matters); submission packet updated; package rebuilt.
- **Fix: Multiple Category Upload (Graphic Links duplicates):** a designer on a published version got two copies of every category. The tool's Submit button stayed clickable while saves were running (the page only reloads after all saves finish), so a repeat click re-posted everything. Submit now locks after the first click, repeated names in one batch are skipped, and the tool initializes once per page. Root cause for her case is not confirmed on the real CMS (it happens only to her, only on Graphic Links); this removes the double-submit path, and the report should be re-checked after she updates.
- **Fix: CSS editor showed `.widgetPH0` (all users, old bug):** `highlightSelector` in `mini-ide.js` swaps parts of a selector for `\x00PH<n>\x00` markers and restored them in one in-order pass. When a `.skinN` marker sat inside a pseudo-class bracket (`:has(.widget.skin61)`) a later marker wrapped it, the inner marker was never restored, and the editor displayed `.widgetPH0`. Markers are now restored repeatedly until none remain. Reproduced and verified against the real function in headless Chrome. The function dates from the March import; this batch did not change it.
- **Fix: `.skin-2` written into CSS for unsaved skins:** an unsaved skin has a temporary ID of -1, -2, -3... but the skin-number logic only treated `-1` as unsaved, in four places (`mini-ide.js`, `widget-skin-advanced-style-helper.js`, `enforce-advanced-styles-text-limits.js`, `css-snippets.js`). A skin with ID -2 got `.skin-2` written into typed CSS, snippets and (new in this batch) the Copy selector button, and a saved skin was never repaired because the replacement pattern `\.skin\d+` ignored the leading minus. Now only a positive whole number is a real skin ID, and `.skin-N` leftovers are replaced with the real ID when a saved skin is opened (a following save is needed to keep it). Verified against the real functions in headless Chrome. The `-1`-only check came from the March import; the Copy selector code reused it.
- **Audit:** every skin default was scanned for visited/normal background mismatches. The only other hit (Calendar Grid Boxes day link) is a hover rule stored in the visited field, which is intended.
